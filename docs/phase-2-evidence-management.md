## Overview

Phase 2 implements the core evidence management system, enabling investigators to collect, store, and verify publicly available evidence with SHA-256 integrity hashing.

**Key Achievement:** Evidence integrity is maintained through immutable content storage and hash verification, establishing a foundation for forensic chain-of-custody principles.

---

## Feature Description

### Evidence Management

The Evidence Management system allows investigators to:

1. **Add Evidence** - Manually add publicly available evidence from various sources
2. **Store Metadata** - Capture source information, publication date, and collection timestamp
3. **Generate Integrity Hash** - Automatically generate SHA-256 hash from stored content
4. **Verify Hash** - Recalculate and verify SHA-256 against stored value to detect tampering
5. **View Evidence** - Display evidence details with all metadata
6. **Manage Evidence** - Delete evidence with proper confirmation

### Source Types Supported

- **News** - News articles, press releases
- **Blog** - Blog posts, personal publications
- **Forum** - Discussion forum posts, Q&A sites
- **Public Social Media** - Twitter, Facebook, LinkedIn (public posts only)
- **Other Public Web Source** - Websites, public databases, etc.

## Data Model

### Evidence Schema

```javascript
{
  _id: ObjectId,
  evidenceId: String,              // EVD-2026-001 (auto-generated)
  investigationId: String,          // Reference to investigation
  sourceName: String,               // e.g., "CNN News"
  sourceType: String,               // News, Blog, Forum, etc.
  sourceUrl: String,                // Publicly accessible URL
  author: String,                   // Source author/attribution
  publicationDate: Date,            // When published
  collectionTimestamp: Date,        // When collected (server-generated)
  content: String,                  // Evidence content (immutable)
  sha256Hash: String,               // SHA-256 hash (immutable)
  notes: String,                    // Editable notes
  analysisStatus: String,           // Pending, Analyzed
  createdAt: Date,                  // Automatic
  updatedAt: Date                   // Automatic
}
```

### Key Design Principles

1. **Immutability**: `content` and `sha256Hash` are set at creation and cannot be modified
2. **Server-Generated Timestamps**: `collectionTimestamp` generated by server, not trusted client time
3. **Auto-Incrementing IDs**: Evidence IDs follow format EVD-YYYY-XXX
4. **Data Integrity**: No silent modifications; if corrections needed, create new evidence record
5. **Relationship**: Each evidence must belong to an existing investigation

## API Endpoints

### Create Evidence

```
POST /api/evidence
```

**Request:**
```json
{
  "investigationId": "INV-2026-001",
  "sourceName": "Tech News Portal",
  "sourceType": "News",
  "sourceUrl": "https://news.example.com/article",
  "author": "Reporter Name",
  "publicationDate": "2026-09-15",
  "content": "Evidence content text...",
  "notes": "Optional notes"
}
```

**Response:**
```json
{
  "message": "Evidence created successfully",
  "evidence": {
    "_id": "...",
    "evidenceId": "EVD-2026-001",
    "investigationId": "INV-2026-001",
    "sha256Hash": "a1b2c3d4...",
    "collectionTimestamp": "2026-10-03T12:30:45.123Z",
    "analysisStatus": "Pending"
  }
}
```

**Validation:**
- `investigationId` must reference existing investigation (400 if not found)
- `sourceName` required, non-empty
- `sourceType` must be valid type (400 if invalid)
- `content` required, non-empty, not whitespace-only
- `sourceUrl` must be valid URL format if provided
- `publicationDate` must be valid date if provided

### Get Evidence by ID

```
GET /api/evidence/:id
```

**Response:**
```json
{
  "evidence": {
    "_id": "...",
    "evidenceId": "EVD-2026-001",
    ...
  }
}
```

---

### Verify SHA-256 Hash

```
POST /api/evidence/:id/verify-hash
```

**Response:**
```json
{
  "evidenceId": "EVD-2026-001",
  "verified": true,
  "storedHash": "a1b2c3d4...",
  "calculatedHash": "a1b2c3d4...",
  "message": "SHA-256 hash verification successful - stored content matches original",
  "timestamp": "2026-10-03T12:30:45.123Z"
}
```

**Hash Mismatch Response:**
```json
{
  "verified": false,
  "message": "SHA-256 hash mismatch - stored content does not match original hash"
}
```

---

### Delete Evidence

```
DELETE /api/evidence/:id
```

**Response:**
```json
{
  "message": "Evidence deleted successfully",
  "evidenceId": "EVD-2026-001"
}
```

## Forensic Purpose

### Integrity Verification

SHA-256 hashing serves as an **integrity reference** for stored evidence:

- **Initial Hash**: Generated when evidence is created from the exact content submitted
- **Verification**: Recalculates hash from current stored content and compares
- **Purpose**: Detects if evidence content has been modified after storage
- **Immutability**: Content cannot be edited; prevents silent modifications

### Chain of Custody Simulation

While not legal evidence, the system demonstrates forensic principles:

1. **Collection Timestamp** - Server-generated (not trusting client time)
2. **Immutable Content** - Evidence cannot be altered after creation
3. **Hash Verification** - Provides integrity check capability
4. **Metadata Preservation** - Source, author, dates tracked
5. **Audit Trail** - Creation and update timestamps recorded

### NOT Legal Admissibility

**Important Disclaimers:**

- SHA-256 does **NOT** prove:
  - Original source authenticity
  - Legal admissibility of evidence
  - Who created the content
  - Non-repudiation

- Hash verification only confirms:
  - Content has not been modified since storage
  - Data integrity in this system

## Known Limitations

### Scope Limitations

1. **No Authentication** - Phase 2 focuses on evidence management; authentication comes later
2. **No Concurrent Editing** - System assumes sequential user interaction
3. **No Batch Import** - Evidence added one at a time (CSV import in future phases)
4. **No Media Support** - Only text content; images/videos in future phases
5. **No Annotation** - Cannot highlight or mark up evidence text

### Forensic Limitations

1. **Not Legal Evidence** - Cannot be used in court as-is; system is academic demonstration
2. **No Chain of Custody** - Multiple users could modify; proper COC tracking needed
3. **No Cryptographic Signature** - Hash provides integrity, not authentication
4. **No Tamper Detection** - No alerts if content modified outside system
5. **Simplified Timestamps** - Client clocks not verified
6. **No Evidence Versioning** - Cannot view modification history

### Technical Limitations

1. **No Caching** - Each request hits database
2. **No Pagination** - Large datasets may slow down
3. **No Rate Limiting** - API open to abuse
4. **No Encryption** - Data stored in plaintext in MongoDB
5. **No Backup Strategy** - No automated backups implemented
